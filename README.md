# VidHarbor v0.1

VidHarbor 是面向单用户、无登录、可信内网部署的视频频道关注、站内更新提醒与视频下载服务。频道功能只支持已经验证的 YouTube 契约；单项直接下载支持固定版本 yt-dlp 能识别并返回必要元数据的 HTTPS 资源。服务不能安全暴露到公网。

## 支持范围

频道地址仅接受以下 HTTPS 格式，且不能带额外路径：

- `https://www.youtube.com/channel/<channel-id>`
- `https://www.youtube.com/@<handle>`

YouTube 单视频地址接受：

- `https://www.youtube.com/watch?v=<11位视频ID>`
- `https://youtu.be/<11位视频ID>`

直接下载还接受任意 HTTPS URL，并由容器内固定版本的 yt-dlp 判断资源是否受支持。资源必须解析为恰好一个条目，并提供非空 `extractor_key`、标题以及可安全用于归档文件名的 ID（仅字母、数字、下划线和连字符）。播放列表不会展开，HTTP 地址、缺少必要元数据的资源以及需要但未提供登录信息的资源会明确失败。

频道首次同步只收录用户选择的最近 1、3、6 或 12 个月内、`live_status=not_live` 的普通 YouTube 视频。Shorts、直播、直播回放以及其他平台的频道订阅不在当前契约内。新视频只产生站内提醒，必须由用户明确选择后才下载。

## 启动

要求 Docker 与 Docker Compose。仓库固定了 Node.js、yt-dlp、FFmpeg 和系统包版本，不应在部署时改用 `latest`。

```sh
docker compose up --build -d
docker compose ps
```

Compose 默认映射到 `http://localhost:3002`。容器健康检查请求既有总览页 `GET /`；它只表示当前进程能够正常提供页面，不代表 YouTube 或代理可达。

服务启动时会检查 `yt-dlp`、`ffmpeg`、SQLite 数据库和 `/downloads` 挂载可用性；任一检查失败都会明确启动失败，不退回其他路径或工具。

部署必须保持单容器、单实例。应用没有登录、用户隔离或权限系统，只能放在访问边界由部署者控制的可信内网中。写接口的同源校验不是身份认证，不得把端口直接映射到公网。

## 持久化挂载

两个挂载缺一不可：

- `/data`：SQLite 数据库，默认文件为 `/data/vidharbor.db`。其中可能含明文代理凭据，宿主机目录权限必须受控并纳入备份。
- `/downloads`：下载根挂载。频道文件归档到 `<downloadRoot>/<频道自定义名称>/<发布年份>/<视频ID>.<扩展名>`，直接下载写入 `<downloadRoot>/<视频ID>.<扩展名>`。

`compose.yaml` 已声明这两个持久卷。若改用 bind mount，需在目标主机上预先创建目录，并确认容器用户具有读取、写入和进入权限。数据库与下载目录不得只保存在容器临时文件系统中。

## 首次配置顺序

1. 启动服务并确认总览页返回 HTTP 200。
2. 在“配置”中设置下载根目录和全局检查间隔。下载根必须是 `/downloads` 本身或其真实子目录；服务不会自动创建配置的根目录，也不会在目录不可用时改用其他位置。
3. 如有需要，再创建命名代理。代理使用固定字段：名称、协议、主机、端口、可选用户名和可选密码；仅支持 `http`、`https`、`socks5`。选择直连时不会自动切换到代理，代理失败时也不会回退到直连。
4. 添加受支持的 YouTube 频道并设置唯一的自定义名称。保存后频道处于“待首次同步”，由用户选择 1、3、6 或 12 个月范围并手工触发；同步在后台执行，只建立历史列表，不产生提醒。
5. 后续检查发现新普通视频后，在提醒或频道页面中由用户明确选择下载；也可以在下载页面提交受支持的单项 HTTPS 资源。

配置中没有 cookies 来源、自动代理选择或代理池。目标站点要求 cookies、发生限流或元数据契约变化时，操作会明确失败，需要管理员检查错误记录。

## 本地验证

默认测试完全离线，使用临时 SQLite、临时下载目录以及假 yt-dlp/FFmpeg；不访问公网，也不使用真实代理凭据。

```sh
npm ci
npm test
npm run build
npm run build:sass
```

真实站点冒烟不属于默认 `npm test`。升级固定的 yt-dlp、FFmpeg、Node.js 基础镜像或原生依赖前，必须在目标 CPU 架构和实际部署网络中另行执行真实冒烟，至少验证 YouTube 频道普通视频元数据、目标平台的单项资源探测、需要 FFmpeg 合并的下载、原子归档和代理/直连各自的预期路径；冒烟成功后才能更新固定版本。不得把未验证架构描述为受支持。

## 运维限制与故障处理

- 进程内调度器和 FIFO 下载 worker 只支持单实例，没有多副本协调能力。
- 下载先写入 `<downloadRoot>/.vidharbor-tmp/<downloadId>/`，只有工具成功、恰好一个非零字节普通文件位于任务目录内、目标不存在时才原子归档。失败任务不会覆盖已有目标。
- 服务重启时遗留的 `pending`、`downloading` 或 `running` 下载记录会标记为 `interrupted`；未完成的首次同步会标记为 `failed`。系统不会自动重试、续传或标记完成，终态记录保持不变。
- 单个频道检查失败不阻断其他频道；单个下载失败不污染其他独立任务。失败不会伪装成“无更新”。
- 支持频道暂停/恢复/删除、下载取消与手工重试、已完成文件预览/下载，以及提醒标记已读。删除已完成下载会永久删除其归档文件和数据库记录；文件缺失或删除失败时保留记录并明确报错。不支持自动重试、自动下载、外部推送、提醒删除或频道 URL 修改。
- `/data` 应做一致性备份并限制宿主机访问；恢复前停止容器。不要在应用运行时复制一个可能仍在写入的 SQLite 文件作为唯一备份。
- 持续监控 `/downloads` 的容量、权限和挂载状态。磁盘耗尽、挂载丢失、目标已存在、零字节输出、路径越界或 yt-dlp/FFmpeg 非零退出都会使对应任务明确失败。
- 宿主文件系统的大小写与 Unicode 语义可能不同。上线前需确认临时目录与最终目录位于同一文件系统，并验证 NFC 目录名、原子且不覆盖目标的硬链接、权限、剩余空间及二进制 CPU 架构一致性。
