# VidHarbor v0.3 产品需求文档

## 功能概述

VidHarbor v0.3 新增独立的 Cookie 登录态管理能力，为当前官方支持的 YouTube、Bilibili、X、Facebook 和抖音各保存最多一份格式正确的 Netscape `cookies.txt`，提供上传、替换、删除、配置状态、更新时间及安全获取说明，但本版不验证远端有效性，也不把 Cookie 注入频道或下载流程；同时从文档、界面和测试契约中撤销 Vimeo 的官方支持与验证承诺，继续保留现有通用 HTTPS 单视频探测能力和旧 Vimeo 下载记录的显示兼容。

## 用户故事

1. 作为需要保存平台登录态的用户，我希望在独立的授权管理入口查看五个受支持平台的 Cookie 配置状态，并上传、替换或删除对应的 `cookies.txt`，以便集中管理每个平台的一份登录态材料。
2. 作为重视凭据安全的用户，我希望系统只展示 Cookie 是否已配置和更新时间，且任何页面、API、日志或错误信息都不返回 Cookie 原文，以免登录态泄露。
3. 作为首次获取 Cookie 的用户，我希望在授权管理入口看到安全的获取与导出说明，并明确知道“已配置”只表示文件已保存且格式正确，不代表登录态仍然有效或已被业务流程使用。
4. 作为直接下载用户，我希望官方支持列表不再承诺 Vimeo 已验证，同时仍可提交符合现有契约的通用 HTTPS 单视频地址，历史 Vimeo 下载记录也能继续正常显示。

## 功能详细说明

### 1. Cookie 登录态管理

#### 1.1 授权管理入口与平台范围

- 界面必须新增明确的“授权管理”入口，并在同一页面固定展示 YouTube、Bilibili、X、Facebook 和抖音五个平台。
- 每个平台只存在一条 Cookie 配置，状态只区分“未配置”和“已配置”。“已配置”仅表示服务器已保存一份通过 Netscape 格式校验的文件。
- 已配置的平台必须展示最后一次成功上传或替换的更新时间；未配置的平台不展示虚构时间。上传或替换失败不得改变原状态或更新时间。
- 授权管理入口不得展示 Vimeo，也不得提供任意平台名称、自定义账号或新增平台的入口。
- 本版只管理 Cookie，不支持多个账号、用户名密码、Token、OAuth、Local Storage、额外请求头或其他授权材料。

#### 1.2 上传与替换

- 未配置的平台提供 `cookies.txt` 文件上传操作；上传成功后状态变为“已配置”，并展示本次成功保存的更新时间。
- 已配置的平台再次上传即替换该平台原有文件，不新增第二份配置。替换必须是完整替换，不合并新旧 Cookie 记录。
- 上传目标平台必须是上述五个平台之一。平台由用户在对应平台项发起操作确定，不从文件内容、域名或文件名猜测。
- 系统只接受 Netscape Cookie 文件，不提供浏览器 Cookie JSON、请求头字符串或其他格式到 Netscape 格式的自动转换。
- 校验和保存必须作为一次完整操作：只有新文件全部校验通过并成功持久化后才替换旧文件；校验或保存失败时保留原文件、原状态和原更新时间。
- 成功结果只返回目标平台、配置状态和更新时间等非敏感元数据，不返回文件内容、Cookie 条目、域名、名称、值或可下载地址。

#### 1.3 Netscape 格式校验

- 上传文件不得为空，也不得只有空白行或注释；去除 Netscape 格式允许的空行和注释后，必须至少包含一条 Cookie 数据记录。
- 每条数据记录必须符合 Netscape `cookies.txt` 的固定七列、制表符分隔格式；字段数量、布尔字段、过期时间及必要字段不符合该格式时，整份文件必须被拒绝。
- Netscape 格式中的标准注释和 `#HttpOnly_` Cookie 记录按该格式本身的语义处理；不得把 `#HttpOnly_` 数据行误判为普通注释。
- 任一数据行损坏都必须拒绝整份文件，不允许忽略坏行后保存剩余内容，也不允许宽松分隔、字段别名、递归解析或猜测式修复。
- 格式校验只证明文件结构正确，不发起平台请求，不检查 Cookie 是否过期、是否属于所选平台、是否能够登录或是否具备访问特定内容的权限。
- 校验失败必须返回稳定的非敏感错误结果，说明文件为空或格式无效即可；错误信息不得回显原始行、字段内容、Cookie 名称、Cookie 值或文件片段。

#### 1.4 删除

- 已配置的平台提供删除操作，界面必须在执行前明确提示目标平台并要求确认。
- 删除成功后该平台立即变为“未配置”，且不再展示原更新时间；其他平台配置不受影响。
- 未配置平台不提供可执行的删除操作。删除失败必须保留原状态，不得向用户报告成功。
- 删除只移除保存的 Cookie 文件及其对应配置元数据，不触发频道、下载、任务或远端平台操作。

#### 1.5 安全获取说明

- 授权管理入口必须为五个平台提供 Cookie 获取与导出说明，指导用户从已登录的平台会话导出 Netscape `cookies.txt` 后，通过对应平台的上传操作保存。
- 说明必须把 Cookie 明确标为等同账号登录凭据的敏感信息，提醒用户只在可信设备上获取和上传，不通过聊天、工单、截图、日志或公开文件传递 Cookie 原文，并在不再需要或怀疑泄露时删除或重新导出替换。
- 说明必须明确本版不会读取浏览器资料目录、不会代替用户登录、不会转换其他授权格式，也不会验证远端有效性。
- 页面必须显著说明本版尚未将已保存 Cookie 接入频道同步、元数据探测或媒体下载；配置成功不会改变这些流程的当前行为。

#### 1.6 明确排除的业务集成

- 频道首次同步、手动检查、定时检查、直接下载元数据探测和媒体下载继续使用现有参数契约，均不得读取或传递本版保存的 Cookie。
- yt-dlp 任务、下载记录和频道记录不得新增 Cookie 配置引用、使用状态或自动选择逻辑。
- 本版不提供远端验证、自动续期、过期提醒、按内容选择 Cookie、跨平台共享、导出、查看或下载已保存 Cookie 的能力。

### 2. 取消 Vimeo 官方支持

#### 2.1 官方范围与用户界面

- 当前官方支持并提供 Cookie 管理的平台固定为 YouTube、Bilibili、X、Facebook 和抖音；Vimeo 不得出现在官方支持、已验证平台或授权管理平台列表中。
- README、项目内说明、下载页面帮助文案、变更说明及其他面向用户的当前能力描述必须移除 Vimeo 的官方支持和真实站点验证承诺。
- 测试名称、固定样例和断言不得再用 Vimeo 证明“官方支持的直接下载平台”或“已验证平台”；需要证明通用直链能力时必须使用中性的通用 HTTPS 样例。

#### 2.2 保留通用 HTTPS 直链探测

- 取消官方支持不等于新增 Vimeo 黑名单。现有直接下载入口仍按当前契约接受 HTTPS 地址，并通过 yt-dlp 探测能否解析为恰好一个具备必要元数据的资源。
- 系统不得仅因 URL 域名或探测结果为 Vimeo 而提前拒绝；其成功与否按通用 HTTPS 直链探测和现有元数据校验结果处理。
- 本需求不扩大通用直链能力：HTTP 地址、主页、播放列表、合集、多条目结果、缺少必要元数据或需要但未提供登录信息的资源仍按现有契约失败。
- Vimeo 不纳入官方冒烟测试矩阵，未来 yt-dlp 版本也不承诺专门验证或修复 Vimeo 兼容性。

#### 2.3 历史记录显示兼容

- 升级前已保存的 Vimeo 下载记录必须继续能在下载列表、详情及数据库浏览等现有读取路径中显示，不得因取消官方支持而被删除、迁移为其他平台或读取失败。
- 现有下载数据的 `platform` 字段继续允许保存和读取非官方平台值；不得新增只允许五个官方平台的数据库约束或显示过滤。
- 前端继续对历史 `vimeo` 平台值提供可理解的显示；对其他未知平台值继续使用现有原值回退显示，不新增平台黑名单。
- 历史记录的取消、重试、删除和文件操作继续遵循其现有状态与数据契约；取消官方支持不改变已存在记录的生命周期。

## 非功能需求

### 安全

- Cookie 原文是最高敏感级别的登录凭据。服务端响应、服务端渲染页面、前端状态、API、日志、异常、测试失败输出和可观测性数据均不得包含 Cookie 文件原文或其中任何字段。
- Cookie 配置列表只允许暴露固定平台标识、是否已配置和更新时间；不得提供预览、部分遮罩值、Cookie 条目数、域名列表、文件路径、文件下载或回读接口。
- 上传、替换和删除继续受现有同源写请求保护；Cookie 文件不得作为静态文件提供，也不得保存在下载目录或其他可由现有文件读取接口访问的位置。
- 持久化文件的访问权限必须限制为运行 VidHarbor 所需的最小范围；替换和删除后不得遗留可被应用继续读取的旧副本。

### 数据一致性与可靠性

- 五个平台的配置必须相互隔离，一个平台的上传、替换、删除或失败不得改变其他平台。
- Cookie 配置必须随现有持久化数据在服务重启和容器重建后保留；不得依赖浏览器本地存储或容器临时文件系统。
- 上传和替换必须避免出现已报告成功但文件不完整、旧文件已丢失或状态元数据与实际文件不一致的中间结果。
- 时间统一使用项目现有时间格式保存，并通过现有前端时间格式展示；只有成功上传或替换才更新配置时间。

### 性能与资源边界

- Cookie 管理操作只处理单个平台的一份上传文件，不得触发任何远端网络请求、yt-dlp 任务、频道任务或下载任务。
- 页面读取配置状态时只返回五个平台的固定元数据，不读取并下发 Cookie 原文。
- 本版不引入 Cookie 后台校验、定时刷新、过期扫描或其他常驻任务。

### 兼容性

- 现有设置、代理、频道、下载和数据库浏览功能的输入输出保持不变；Cookie 管理使用独立契约，不向现有完整设置对象追加猜测字段。
- 现有部署的持久化数据升级后必须保留，尤其不得收紧下载记录平台字段为官方平台枚举。
- 取消 Vimeo 官方支持只改变文档、界面和测试承诺，不改变通用 HTTPS URL 校验、yt-dlp 探测或历史数据读取规则。

### 可观测性与错误处理

- 上传、替换和删除的成功与失败必须可由调用方明确感知；格式错误属于输入校验失败，持久化失败属于服务端失败，不得静默忽略或报告为已配置。
- 可记录操作类型、目标固定平台、成功或失败及发生时间，但不得记录上传文件名、文件内容、Cookie 字段、服务端保存路径或能够还原登录态的信息。
- 未确认的平台、授权类型、输入格式和操作必须显式拒绝，不得通过别名、自动推断、兼容层或 fallback 接受。

### 验收与测试边界

- 测试必须证明五个平台各自最多保存一份 Cookie，并覆盖未配置、首次上传、成功替换、删除及更新时间变化。
- 测试必须覆盖空文件、纯注释文件、非 Netscape 格式、字段数错误、非法字段和含损坏行的混合文件均被拒绝，同时证明有效 Netscape 文件及 `#HttpOnly_` 记录可被接受。
- 测试必须证明上传或替换失败时旧文件和旧更新时间保持不变，删除失败时仍为已配置，且一个平台的操作不影响其他平台。
- 页面和 API 测试必须断言只返回配置状态和更新时间，不出现 Cookie 原文、字段、文件路径、预览或下载能力；日志和错误测试必须使用敏感标记证明原文不会泄露。
- 测试必须证明保存 Cookie 后不会改变频道、元数据探测和下载任务参数，也不会产生远端验证或后台任务。
- 测试必须证明 Vimeo 已从当前文档、界面、官方平台与验证矩阵中移除，同时通用 HTTPS 样例仍可探测，历史 `vimeo` 记录仍可显示且未知平台值继续回退显示。
