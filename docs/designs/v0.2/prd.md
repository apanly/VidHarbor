# VidHarbor v0.2 产品需求文档

## 功能概述

VidHarbor v0.2 将当前分散在媒体下载、单项资源元数据探测、频道首次同步、频道手动检查和频道定时检查中的 yt-dlp 调用收口到唯一的 yt-dlp 管理器。管理器统一接收任务、维护 `queued`、`running`、`succeeded`、`failed`、`canceled` 生命周期，并负责取消与服务停止时的收尾；界面统一展示排队中和运行中的任务、任务类型及执行结果。媒体下载继续使用现有 `download_concurrency` 并发限制，其他任务不限制并发且不与下载共享额度；`src/yt-dlp.ts` 仅保留固定参数构造、子进程执行和输出解析职责。

## 用户故事

1. 作为下载用户，我希望媒体下载继续遵守已配置的下载并发数，同时频道同步和检查不占用下载名额，以便不同用途的 yt-dlp 操作互不阻塞。
2. 作为频道管理用户，我希望首次同步、手动检查和定时检查都进入同一个任务管理入口，以便能够从统一界面判断任务是在排队、运行、成功、失败还是已取消。
3. 作为服务维护者，我希望所有 yt-dlp 子进程都由同一个管理器负责取消和停机收尾，以便服务停止时不会遗留失管进程或继续启动新任务。
4. 作为开发维护者，我希望业务模块只能向管理器提交 yt-dlp 任务，而底层 `src/yt-dlp.ts` 只处理固定执行协议，以便调度规则和进程细节边界清晰且可集中验证。

## 功能详细说明

### 1. 唯一的 yt-dlp 任务提交入口

- 系统必须只有一个负责 yt-dlp 任务管理与调度的入口。媒体下载、元数据探测、频道首次同步、频道手动检查和频道定时检查均必须通过该入口提交。
- 纳入范围包括上述流程中实际启动的全部 yt-dlp 子进程；业务模块不得直接调用 `src/yt-dlp.ts` 绕过管理器启动进程。
- 管理器负责调度、任务生命周期、取消和服务停止收尾。业务模块仍负责各自已有的输入校验、业务数据读写和业务结果解释，不把这些职责转移到 `src/yt-dlp.ts`。
- 本版只收口当前已经存在的五类任务，不增加新的抓取、下载、自动重试或任务编排能力。

### 2. 五类任务及统一生命周期

- 管理器必须能区分并展示五类任务：媒体下载、元数据探测、频道首次同步、频道手动检查、频道定时检查。
- 每个提交给管理器的任务只使用以下生命周期状态：`queued`、`running`、`succeeded`、`failed`、`canceled`。
- 新任务被接受后进入 `queued`；实际开始执行 yt-dlp 时进入 `running`；正常完成进入 `succeeded`；执行或输出处理失败进入 `failed`；在开始前或运行中被取消进入 `canceled`。
- `succeeded`、`failed`、`canceled` 是终态，任务到达终态后不得再次运行或改写为其他终态。重试仍由现有业务操作重新提交一个任务，不复用已终止任务。
- 失败必须保留可供现有业务错误边界和界面结果展示使用的原因，不得把失败标记为成功或静默丢弃。单个任务失败不得自动取消或阻断其他独立任务。
- 统一任务状态用于描述管理器中的 yt-dlp 执行过程，不替换现有下载记录、频道首次同步状态和频道检查结果；这些业务状态仍按现有契约更新，并与对应任务的最终执行结果保持一致。

### 3. 分离的并发规则

- 媒体下载继续使用设置中的现有 `download_concurrency` 作为唯一并发上限；达到上限的媒体下载保持 `queued`，并按提交顺序等待下载名额。
- 元数据探测、频道首次同步、频道手动检查和频道定时检查不设置并发上限，提交后由管理器直接调度执行。
- 非媒体下载任务不占用 `download_concurrency` 名额；媒体下载也不得限制其他四类任务启动。各类任务不共享并发额度。
- 本版不设置任务优先级，不增加按任务类型、来源平台或触发方式抢占、加权或预留名额的规则。
- 现有“同一频道不得重复执行定时检查”等业务防重边界继续由对应业务模块负责，不扩展为管理器中的通用去重或合并机制。

### 4. 统一取消

- 所有已提交任务的取消都必须由管理器处理，业务模块不得自行持有并直接终止 yt-dlp 子进程。
- 取消 `queued` 任务时，管理器必须将其从待执行集合中移除，标记为 `canceled`，且不得再启动对应 yt-dlp 进程。
- 取消 `running` 任务时，管理器必须终止该任务所属的 yt-dlp 进程及其进程组，等待执行结束并将任务标记为 `canceled`。
- 现有媒体下载取消入口继续可用，并改为调用统一管理器；取消后的下载业务记录仍按现有 `canceled` 契约保存原因和完成时间。
- 原始需求只确认现有媒体下载的用户取消入口；本版不新增其他任务类型的界面取消按钮。其他任务仍须具备供停机收尾使用的管理器取消能力。

### 5. 服务停止收尾

- 服务进入停止流程后，管理器必须拒绝接受新的 yt-dlp 任务，并停止从队列启动尚未运行的任务。
- 停止流程必须通过同一管理器取消仍处于 `queued` 或 `running` 的任务，并等待相关 yt-dlp 子进程退出及任务状态完成收敛后，才能关闭其依赖的运行时资源和数据库连接。
- 停止流程应可重复调用而不重复启动取消动作或产生第二套收尾流程。
- 服务重启后，下载和频道首次同步等业务记录仍按现有恢复契约处理；本版不增加自动续跑、自动重试或断点续传。

### 6. 统一任务状态展示

- 界面必须提供统一的 yt-dlp 任务状态视图，至少展示当前排队任务、当前运行任务、每项任务的任务类型，以及已结束任务的 `succeeded`、`failed` 或 `canceled` 执行结果。
- 状态名称和任务类型必须来自管理器的同一份任务快照，不得由前端根据下载记录或频道记录猜测管理器状态。
- 任务从 `queued` 进入 `running`、从活动状态进入终态后，界面应能通过刷新或现有页面更新机制取得最新状态；失败任务必须展示经过现有敏感信息脱敏规则处理的失败原因。
- 下载页面现有下载记录、进度、取消、重试和文件操作继续保留；统一任务状态视图不删除或改写这些业务功能。
- 原始需求未指定新的筛选、搜索、分页、排序、历史保留期限或统计图表，本版不增加这些交互。

## 非功能需求

### 性能与资源

- `download_concurrency` 只约束媒体下载，且升级后不得改变其已配置数值及现有限流语义。
- 非媒体下载任务按明确需求不限制并发；本版不另设隐含全局上限、跨类型共享池或任务优先级。
- 管理器必须在任务结束后释放对应子进程、取消监听和运行态引用，避免已终止任务继续占用执行名额或阻止服务停止。

### 兼容性与职责边界

- 现有下载、元数据探测、首次同步、手动检查和定时检查的输入、输出、业务状态、错误码及触发方式保持不变；本版只统一其 yt-dlp 提交、调度和执行状态管理。
- `src/yt-dlp.ts` 只保留已确认的固定参数协议、无 shell 的进程执行、超时与取消信号处理、标准输出/错误输出处理及结果解析，不保存业务任务状态，不读取下载并发配置，也不判断任务类型。
- 调度逻辑、任务类型和生命周期不得在业务服务、下载 worker、频道 scheduler 与 `src/yt-dlp.ts` 之间形成多套实现。

### 安全与稳定性

- 继续使用参数数组启动 yt-dlp，禁止把用户输入拼接为 shell 命令。
- 取消和停机必须终止完整进程组，不得只结束父进程而遗留 yt-dlp 派生进程。
- 代理凭据及其他敏感信息继续使用现有脱敏规则处理；统一任务状态和失败结果不得暴露完整凭据。
- 未确认的任务类型、生命周期状态或调度选项必须显式拒绝，不得通过别名、宽松解析或 fallback 接受。

### 可观测性与错误处理

- 管理器必须能提供足以支撑界面展示的当前任务状态、任务类型和执行结果，并使状态变化可被测试稳定观察。
- yt-dlp 启动失败、非接受退出码、超时、输出解析失败和取消必须分别落入已确认的 `failed` 或 `canceled` 终态，不得留下永久 `queued` 或 `running` 状态。
- 一个任务的业务失败由对应业务边界处理；只有管理器自身无法继续调度或维护状态的系统级错误才进入现有运行时故障上报边界。

### 验收与测试边界

- 测试必须证明五类现有流程都通过唯一管理器提交，业务模块不存在绕过管理器直接启动 yt-dlp 的路径。
- 测试必须覆盖 `queued -> running -> succeeded`、执行失败进入 `failed`、排队取消和运行中取消进入 `canceled`，并证明终态不会再次转换。
- 测试必须证明媒体下载严格受 `download_concurrency` 限制，超额任务保持排队；其他四类任务可并发启动、不消耗下载名额，且没有任务优先级。
- 测试必须覆盖服务停止时拒绝新任务、取消排队及运行任务、等待进程退出，以及重复停止的边界。
- 测试必须证明界面能展示排队任务、运行任务、五种任务类型和三种终态结果，且失败原因不泄露代理凭据。
- 测试必须证明原有下载取消与重试、频道首次同步、手动检查、定时检查和重启恢复的业务契约保持有效；未确认的任务类型、状态和调度格式不受支持。
